Playful JS course design notes

- The diagrams must stay behaviorally faithful to JavaScript execution. Do not skip a state if skipping it would teach a false mental model.
- Assignment should be shown as: create/identify the left-side variable or property, evaluate the right-side expression, then point the left-side wire to the resulting value.
- Function calls should show the call sequence clearly: the function value is evaluated, arguments are evaluated, parameters are created in the call frame, the body returns a value, and only then does the receiving variable point to the returned value.
- Avoid visual shortcuts where a variable or value appears "magically" without the explanation step naming what JavaScript just did.
- Keep visual conventions consistent across chapters: variables are boxes, primitive values are circles/pills, objects/functions are object-like values, and wires represent references to values.
- Visible variable boxes and primitive value nodes must use a full white background, never opacity-based dimming. Hidden future-step nodes should be fully hidden, not ghosted.
- Every chapter should be understandable to a beginner learning JavaScript for the first time, while still being accurate enough not to create misconceptions.
- Every example must demonstrate why its feature is useful, not merely prove that the syntax runs. When simpler syntax would produce the same lesson outcome, either use the simpler syntax or make the chapter's distinct benefit observable in code and in the diagram.
- Do not end a practical example at an unused method call or property read when its result is the point of the lesson. Store, render, return, or otherwise visibly use the result so the learner can follow the complete execution.
- Keep simple examples when they isolate one new mechanism, but do not let simplicity remove the real behaviour that distinguishes the feature: inherited lookup must call an inherited method, narrowing must use the narrowed property, and uniqueness must have an observable result.
- Introduce a new technical term in plain language before relying on it. Do not assume that words such as callback, accumulator, prototype, compile-time, Promise, DOM, task, or microtask are already understood.
- Keep function-call vocabulary precise: a function name is a binding used to find a function value, a parameter is a local binding declared by the function, and an argument is the expression or value supplied at the call site. A callback is a function value used as an argument so other code can call it.
- Treat wires as a teaching notation for a binding or property holding a value. They are not claims about a JavaScript engine's physical memory layout.
- Distinguish bindings from values. `let`, `const`, function declarations, parameters, imports, and `catch` parameters create bindings. Objects, functions, strings, numbers, booleans, `null`, `undefined`, symbols, and bigints are values.
- Primitive values are immutable and do not expose object identity. Two occurrences of the same primitive, such as `"Grace"`, are the same language-level value; do not describe them as shared mutable storage or as two observable copies.
- Objects and functions have identity. Two bindings can refer to the same object, so a property mutation through either binding is visible through the other. Reassignment moves one binding to another value and does not mutate the old object.
- Be explicit about abstraction boundaries. Browser APIs, timer registries, event-listener lists, Promise reaction queues, module records, and engine internal slots are host/runtime machinery, not ordinary JavaScript properties. Label them as host or internal state and do not draw property wires to them.
- `this` is a special value supplied for a function call, not an ordinary parameter written in the function's parameter list. Arrow functions do not create their own `this` binding.
- Explain short-circuit operators accurately: `&&` and `||` select and return one of their operand values. They return booleans only when the selected operand is boolean. `!` always returns a boolean.
- A callback's return value does not automatically become the enclosing function's return value. Show whether the caller returns it, stores it, uses it to settle a Promise, or ignores it.
- Every binding, object, call, and state change shown in a diagram must come from visible code, or be clearly marked as host/runtime or internal state. Do not invent an executed call or object that the snippet never creates.
- When code relies on a particular context, state it. Top-level `await` requires module code; browser globals require a browser; TypeScript annotations are removed before JavaScript runs.
- Describe garbage collection through reachability, not immediate destruction. An unreachable object becomes eligible for collection; JavaScript does not expose exactly when collection happens.
- Prefer one execution change per lesson step. If a sentence needs to describe several calls, assignments, or state changes, split it unless the combined view is explicitly a recap.
- Visible chapter titles should be unique. If two nearby chapters teach the same underlying idea, rename, repurpose, merge, or reorder them so each chapter has a clear reason to exist.
- Before adding a chapter, search both practical and concept lessons for duplicate topics. Add a chapter only when it teaches a distinct everyday skill or a necessary mental model.
